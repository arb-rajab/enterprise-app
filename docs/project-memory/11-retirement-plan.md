# Retirement Plan

This document exists because the SDLC documentation pattern for this portfolio requires stating,
honestly, what happens when a project is no longer maintained — even (especially) for a
portfolio/demo repository that was never going to run in production.

## What this project is, for retirement purposes
ProcureFlow is a **skill-demonstration artifact**, not a running service. There is no production
deployment, no real user data, no third-party integration, and no scheduled job or external
dependency that continues to run or cost money after the repository stops being touched. Its
"operational footprint" when idle is exactly zero — it is source code and documentation sitting in
a Git repository.

## Data
No real data exists. The only data the project ever creates is:
- Whatever a reader seeds into their own local `docker compose up` Postgres volume (an isolated,
  local Docker volume, never shared or synced anywhere).
- The seed/demo data in `V2__seed_reference_data.sql`, which is fictional (fictional company,
  fictional vendors, one shared throwaway password) by design.

There is nothing to export, migrate, or delete on retirement — no live database, no user accounts
tied to real people, no PII.

## Secrets
No real secret was ever issued for this project. The JWT signing secret is generated by whoever
runs it locally (`.env`, git-ignored); there is no shared/production secret to rotate or revoke on
retirement.

## Retirement procedure
If this repository is archived or deleted:
1. Nothing external needs to be notified — no running deployment, no DNS record, no third-party
   webhook or integration points at it.
2. If a reader has a local `docker compose` volume from having run it, `docker compose down -v`
   removes it; nothing survives outside that machine.
3. Simply archiving the GitHub repository (or deleting it) is sufficient; there is no phased
   decommissioning needed because nothing depends on this repository staying available.

## If this were ever promoted from demo to a real product
The honest answer is that most of `09-backlog.md` would need to be done first (row-level
authorization, JWT revocation, rate limiting, a real deployment target with monitoring/backups),
and *this* retirement plan would need to be rewritten entirely around real data-retention and
secret-rotation obligations, because none currently exist to describe.
